# AGENTS.md

## 1. О проекте

MTS Energytool — frontend веб-приложения ИИ-консультанта по энергетическим решениям.

Основная задача интерфейса — позволить пользователю:
- Начать новый диалог с ИИ-консультантом.
- Описать свою задачу или проблему в сфере энергетики.
- Получать ответы и уточняющие вопросы от консультанта.
- Просматривать историю предыдущих диалогов.
- Передавать контактные данные для связи со специалистом.
- Просматривать итоговую информацию по заявке.

Интерфейс должен быть простым, понятным и удобным для пользователей с разным уровнем технической подготовки.

## 3. Архитектура проекта

Используй подход Feature-Sliced Design (FSD).

Основные слои:

- `app` — инициализация приложения, роутинг, глобальные провайдеры, глобальные стили.
- `pages` — страницы приложения.
- `widgets` — крупные самостоятельные блоки интерфейса.
- `features` — пользовательские действия и бизнес-сценарии.
- `entities` — бизнес-сущности и связанные с ними модели, API и UI.
- `shared` — переиспользуемые компоненты, утилиты, конфигурации и типы.

Пример структуры:

```text
src/
├── app/
│   ├── providers/
│   ├── router/
│   ├── styles/
│   └── App.tsx
│
├── pages/
│   └── chat/
│
├── widgets/
│   ├── header/
│   ├── sidebar/
│   └── chat/
│
├── features/
│   ├── create-chat/
│   ├── send-message/
│   └── submit-lead/
│
├── entities/
│   ├── chat/
│   ├── message/
│   └── lead/
│
└── shared/
    ├── api/
    ├── ui/
    ├── lib/
    ├── types/
    └── config/
```

Это ориентир, а не требование создавать все директории заранее.

### Правила архитектуры

- Соблюдай направление зависимостей FSD.
- Не размещай бизнес-логику в UI-компонентах без необходимости.
- Не смешивай API-запросы, состояние и отображение в одном большом компоненте.
- Переиспользуемую логику выноси в соответствующий слой.
- Не создавай абстракции ради абстракций.
- Не дублируй компоненты и бизнес-логику.
- Не переноси существующие файлы без реальной необходимости.
- Используй публичные API сегментов через `index.ts`, если это соответствует текущей архитектуре проекта.

## 4. TypeScript

Используй TypeScript во всех React-компонентах и модулях, где это применимо.

Правила:

- Не используй `any`.
- Не отключай проверки TypeScript ради устранения ошибок.
- Не используй `@ts-ignore` без веской причины.
- Для объектов, передаваемых между компонентами, определяй интерфейсы или типы.
- Типизируй props компонентов.
- Типизируй аргументы и возвращаемые значения функций, когда это повышает понятность.
- Используй объединения типов для ограниченного набора состояний.
- Не дублируй одинаковые типы в разных файлах.

Предпочитай понятные и конкретные названия типов.

Пример:

```ts
export interface Chat {
  id: string;
  title: string;
  updatedAt: string;
}
```

## 5. React

- Используй функциональные компоненты.
- Соблюдай правила React Hooks.
- Не используй прямые манипуляции DOM без необходимости.
- Не создавай лишние состояния, если значение можно вычислить.
- Не используй `useEffect` для логики, которую можно реализовать непосредственно при обработке события или через вычисление данных.
- Не добавляй `useMemo` и `useCallback` без обоснованной необходимости.
- Разделяй большие компоненты на небольшие логические части.
- Не допускай лишних повторных запросов и рендеров.
- Используй корректные `key` при рендеринге списков.

Старайся делать компоненты предсказуемыми и простыми для поддержки.

## 6. Управление состоянием

Используй Redux Toolkit для общего состояния приложения.

RTK Query используй для взаимодействия с backend API.

Локальное состояние компонента через `useState` подходит для:
- Открытия и закрытия модальных окон.
- Состояния выпадающих списков.
- Локальных UI-переключателей.
- Временных значений форм.

Не дублируй одни и те же данные одновременно в Redux и локальном состоянии без необходимости.

Не храни в Redux данные, которые нужны только одному небольшому компоненту.

## 7. Работа с API

Все запросы к backend должны быть организованы централизованно.

Предпочтительно использовать RTK Query.

Правила:

- Не вызывай `fetch` непосредственно внутри UI-компонентов.
- Не хардкодь URL backend в компонентах.
- Используй переменные окружения для конфигурации API.
- Не выдумывай API-эндпоинты и структуру ответов.
- Перед реализацией интеграции изучай существующие API-контракты.
- Обрабатывай состояния загрузки, ошибок и пустых результатов.
- Не скрывай ошибки запросов.
- Не храни секреты и токены в репозитории.

Если backend-контракт ещё не определён, используй временные mock-данные с явным отделением от реального API.

Не создавай фиктивную интеграцию, которая выглядит как работающий backend.

## 8. Стилизация

Используй SCSS Modules для стилей компонентов.

Пример:

```text
Sidebar/
├── Sidebar.tsx
└── Sidebar.module.scss
```

Импорт стилей:

```tsx
import styles from './Sidebar.module.scss';
```

Применение:

```tsx
<div className={styles.sidebar}>
  ...
</div>
```

Правила:

- Не используй глобальные стили для отдельных компонентов.
- Не используй inline-стили.
- Не добавляй обычные CSS-файлы вместо SCSS Modules.
- Используй существующие глобальные CSS-переменные.
- Не дублируй значения цветов, если для них уже есть переменные.
- Используй вложенность SCSS умеренно.
- Не создавай чрезмерно сложные селекторы.
- Не используй `!important`, если проблему можно решить правильной специфичностью.
- Обязательно учитывай адаптивность.

В приложении предусмотрены светлая и тёмная темы.

- Учитывай обе темы при разработке новых компонентов.
- Не используй жёстко заданные цвета для поверхностей, текста и границ, если для них предусмотрены тематические переменные.
- Не изменяй существующий механизм переключения темы без необходимости.
- Проверяй контрастность элементов в обеих темах.

## 9. UI и UX

Интерфейс должен соответствовать следующим требованиям:

- Единый визуальный стиль.
- Предсказуемое поведение элементов.
- Понятные состояния загрузки.
- Понятные сообщения об ошибках.
- Пустые состояния для списков и истории.

- Корректная работа на мобильных устройствах.
- Отсутствие горизонтальной прокрутки без необходимости.

Не добавляй декоративные элементы, которые мешают основному пользовательскому сценарию.

Соблюдай семантику HTML.

Для интерактивных элементов используй подходящие HTML-теги: `button`, `input`, `form` и другие.

Не используй `div` вместо кнопки, если элемент выполняет действие.

Учитывай доступность: `aria-label`, `aria-expanded`, `aria-pressed` и другие подходящие атрибуты.

## 10. Основные сценарии приложения

При разработке учитывай следующие сценарии.

### Чат

- Пользователь отправляет сообщение.
- Отображается состояние отправки.
- Полученный ответ отображается в истории сообщений.
- История текущего диалога сохраняется.
- При ошибке запроса пользователь получает понятное уведомление.
- Контекст сохраняется в рамках одного диалога.

### История диалогов

- Пользователь может создавать новые диалоги.
- Пользователь может переключаться между существующими диалогами.
- Активный диалог визуально выделяется.
- История сохраняется даже в том случае, если пользователь не оставил заявку.
- Новый диалог не должен удалять предыдущие диалоги.

### Заявка

Для передачи заявки предусмотрены:
- ФИО.
- Телефон.
- Компания.

После получения данных должна быть предусмотрена возможность отображения итоговой информации и краткого резюме диалога.

Не реализуй отправку заявки на несуществующий endpoint.

### Debug-режим

Предусмотри отображение отладочной информации, если она предоставляется backend:

- Время ответа.
- Использованные документы базы знаний.

Не выдумывай значения отладочной информации.

## 11. Работа с формами

Для форм используй существующие библиотеки проекта, если они уже установлены.

Правила:

- Валидируй пользовательский ввод.
- Показывай ошибки рядом с соответствующими полями.
- Не отправляй заведомо некорректные данные.
- Не очищай форму до успешного завершения операции, если это может привести к потере введённых данных.
- Не дублируй правила валидации на frontend, если они уже централизованы и могут быть переиспользованы.

Используй понятные и последовательные названия.

При работе с проектом:

- Не удаляй существующую функциональность без согласования.
- Не перезаписывай пользовательские изменения.
- Не добавляй секреты, `.env` и персональные данные в Git.
- Учитывай существующий `.gitignore`.

- Не создавай коммиты самостоятельно, если пользователь явно этого не просил.

## 14. Порядок выполнения задач

Перед реализацией каждой задачи:

1. Изучи связанные компоненты и существующую структуру.
2. Проверь `package.json` и доступные зависимости.
3. Найди существующие решения, которые можно переиспользовать.
4. Определи минимальный набор необходимых изменений.
5. Учитывай текущие архитектурные соглашения.

Во время реализации:

1. Делай изменения небольшими и логически разделёнными.
2. Не переписывай рабочий код без необходимости.
3. Не добавляй лишнюю абстракцию.
4. Следи за типизацией.
5. Проверяй адаптивность и обе темы оформления.

После реализации:

1. Проверь TypeScript.
2. Запусти ESLint, если настроен.
3. Запусти сборку проекта.
4. Исправь ошибки, возникшие после изменений.
5. Сообщи, какие файлы были созданы и изменены.
6. Кратко объясни принятые решения.
7. Укажи, если остались задачи, требующие backend или дополнительных данных.

Не утверждай, что проверки прошли успешно, если фактически их не запускал.

- Не усложняй код без необходимости.
- Не создавай дополнительные файлы ради формального соблюдения архитектуры.
