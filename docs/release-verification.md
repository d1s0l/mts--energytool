# Проверка заявки и ZIP перед сабмитом

Универсальный запуск из корня репозитория, в окружении backend requirements-dev.txt:

```sh
python backend/verify_release.py --env /path/to/env --kb /path/to/knowledge-base.zip \
  --questions /path/to/demo_questions.csv --approved-requirements /path/to/requirements.txt \
  --output-root /tmp/energytool-release
```

Локально для этой задачи: `bash /root/folder_for_q/run_release_check.sh`.
Скрипт сам выбирает venv и отдельную рабочую копию fix/submission-lead-verification.
`--offline` ограничивает запуск офлайн-проверками; такой отчёт имеет статус
offline_complete и не означает, что настоящая модель или PostgreSQL проверены.

Полный запуск включает:

1. Регрессионные тесты ядра, памяти, лимитов, диагностики и сабмита; тесты RAG.
2. Сборку настоящего плоского submission.zip: только корневые модули Python и
   requirements.txt, проверка синтаксиса и разрешённых фиксированных зависимостей.
3. Backend pytest с настоящей тестовой PostgreSQL. Можно передать TEST_DATABASE_URL;
   иначе запускается отдельный Compose-проект energytool-diagnostics на порту 55432.
4. `verify_live_api.py`: настоящая модель, HTTP-маршруты приложения и настоящая БД.
   Проверяются сохранение 45 счётчиков, отказ, согласие, создание заявки, замена
   телефона, одна карточка заявки, повтор HTTP-запроса без повторного вызова модели,
   разные объекты, новый диалог и доступность старой истории. Для проверки создаётся
   уникальная схема verify_*, которая удаляется в finally. Действия заявки не симулируются.
5. `verify_submission.py`: ZIP распаковывается во временный каталог вне репозитория;
   запускается его `python solution.py` без PYTHONPATH и без backend/БД. Передаются
   18 демо-вопросов и 4 дополнительных входа с контактами: готовая заявка, отказ,
   неполные контакты и исправленный телефон. Работает настоящая модель.

CSV проверяется на ровно две колонки id/answer, порядок и полноту ID, непустые
ответы и лимит 10000 символов. Техническая заглушка считается ошибкой. Для
контактных случаев проверяются наличие заявки и актуального телефона, отсутствие
заявки после отказа или при неполных контактах. Эти проверки не доказывают смысловую
правильность всех продуктовых ответов; ответы и источники нужно также просматривать.

Артефакты в release-<commit>-<fingerprint>: manifest.json, журналы этапов,
archive-audit.json, submission.zip, live-api.json, packaged-model.json и CSV.
Только status=complete означает прохождение всех требуемых этапов. Пропуски,
недоступность сети/БД, ошибки модели и неверные бизнес-результаты дают partial.
Один лишь успешный HTTP-ответ больше не считается доказательством создания заявки.

Офлайн-тест полного ZIP использует подставной HTTP-транспорт, а тест цепочки заявки
симулирует подтверждение сохранения. Они явно отделены от live-api и packaged-model.
В отчёте сохранены фактические версии установленных библиотек; локальный pydantic
может отличаться патч-версией от разрешённой платформой версии в ZIP.

Генерация, исправление и проверка ответа используют общий бюджет 55 секунд,
укладывающийся в таймаут HTTP-маршрута. Повторы HTTP-запросов ограничены оставшимся
бюджетом. CSV-адаптер оставляет запас до платформенного ограничения 20 минут.
Резюме для формы заявки использует отдельный бюджет 50 секунд с возвратом
к дословным сообщениям пользователя при недоступности модели. Отсутствие
необязательного lead_facts не отменяет готовую заявку: используются проверенные
параметры объекта либо исходные сообщения клиента. Явно переданные выдуманные
цитаты при этом по-прежнему отклоняются.
LLM_MIN_INTERVAL задаёт необязательный минимальный интервал между вызовами модели;
в проверке ZIP он по умолчанию нулевой и MAX_WORKERS=1. Искусственная пауза перед
каждым запросом не добавляется в минутный бюджет ответа; для отдельного исследования
лимитов провайдера можно передать --interval. Профиль запуска сохраняется в JSON.
В ZIP нет встроенных данных, ключей или фиксированной модели.

При HTTP 429 CSV-адаптер ждёт Retry-After и повторяет вопрос не более двух раз,
только если остаётся время до общего дедлайна. Проверка живого API также повторяет
тот же client_message_id после cooldown; новые ходы проверки начинаются с интервалом
не менее 45 секунд, вне минутного бюджета HTTP-ответа. Это ограничение нагрузки
тестового клиента, а не задержка обычного чата. Подтверждение уже проверенной заявки
формирует приложение; дополнительный LLM-вызов для этого служебного текста не нужен.
Проверка продуктовых ответов остаётся включённой.

Проверяющая модель может предложить удаление целых дословных предложений из уже
проверенного ответа и отдельно подтвердить все четыре критерия для оставшегося
текста с прежним вопросом. Сервер принимает только такое удаление: не принимает
новый текст, удаление отдельных слов, пустой остаток или неподтверждённое сохранение
оговорок. Числа, предметные ограничения и совместимость проверяются повторно.
Это позволяет убрать неподтверждённое пояснение без двух новых LLM-вызовов.
По умолчанию передаётся reasoning_effort=none; параметр проверен реальным запросом
к настроенному прокси. Явное LLM_REASONING_EFFORT переопределяет его.
[Документация vLLM](https://docs.vllm.ai/en/latest/features/reasoning_outputs/#automatic-enable_thinking-activation)
различает low (рассуждение включено) и none (выключено для поддерживающих это шаблонов).
На том же проверочном запросе настроенный прокси вернул ответ с none за 1,37 секунды;
это отдельный замер, а не гарантия времени для любого запроса.
В памяти отмечаются также вопросы, для которых нет заранее заданного поля:
используется короткий идентификатор текста с областью объекта. Это предотвращает
ошибку повторного уточнения и лишнюю генерацию. Отказ от контакта удерживает
состояние chatting, чтобы интерфейс не открывал форму контактов повторно.
Для проверки самого ZIP можно передать --submission-python в verify_release.py
(или --python в verify_submission.py): это интерпретатор отдельного окружения
с установленными точными requirements.txt. Его версии сохраняются в отчёте.
Проверка чисел сопоставляет русские количественные числительные с цифрами и учитывает
масштаб: «сорока» и 40 эквивалентны, «сорок тысяч» и 40 — нет. Подтверждение чисел
по цитатам и проверка смысловых условий остаются обязательными.
После 429 CSV-адаптер применяет общий cooldown не менее минуты и адаптирует темп
новых вопросов до одного в 45 секунд. В локальной проверке ZIP такой темп включён
сразу; паузы происходят до начала минутного бюджета ответа. Между API-проверкой
и запуском ZIP выдерживается минута, чтобы одна проверка не исчерпывала лимит другой.
