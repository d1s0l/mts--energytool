# Полная диагностика

На машине с доступом к модели, в активном Python venv:

```sh
cd /root/folder_for_q/mts--energytool
python -m pip install -r backend/requirements-dev.txt
bash /root/folder_for_q/run_full_check.sh
```

Локальный launcher использует `/root/folder_for_q/_env.uu`, базу и демо-вопросы в
`/root/folder_for_q/Данные`. Универсальный вариант из репозитория:

```sh
python backend/collect_diagnostics.py --env /path/to/env \
  --kb /path/to/knowledge-base.zip --questions /path/to/demo_questions.csv \
  --output-root /tmp/energytool-diagnostics
```

Обычный прогон включает:

1. Офлайн-тесты памяти, консультации, ошибок и диагностических инструментов.
2. Офлайн-тесты RAG.
3. Backend pytest с настоящим PostgreSQL, если установлены dev-зависимости и
   задан TEST_DATABASE_URL или DATABASE_URL. Используются только временные схемы
   с уникальными именами; основная схема приложения не мигрируется этими тестами.
   Учётной записи нужны права создавать/удалять эти тестовые схемы.
4. Ответы модели на 18 независимых демо-вопросов.
5. 11 реальных ходов в двух сценариях: сбор задачи и контактов, исправление
   количества приборов, отказ от телефона, последующее оформление заявки,
   исправление телефона; два раздельных объекта, возврат к первому и новый диалог.

Запись заявки в многошаговом модельном прогоне **симулируется** и явно отмечена
в JSON. SQL, атомарность, сохранение памяти и повтор запроса проверяются backend
pytest с реальной БД и подставными ответами модели. Этот набор не заменяет проверку
развёрнутого API с настоящей моделью одновременно и ручное тестирование сайта.

Результаты находятся в одной папке `full-check-<commit>-<fingerprint>`:

- manifest.json — версия кода, параметры модели без секретов, версии пакетов,
  результат каждого этапа и факт пропущенных проверок;
- offline-core.log, offline-rag.log — полный вывод офлайн-тестов;
- postgres-api.log — миграции/API/БД: результат pytest или причина пропуска;
- answers.json и answers.log — одиночные вопросы, источники, память, ответы и ошибки;
- dialogs.json и dialogs.log — многошаговые диалоги, память до/после каждого хода,
  действия заявки, источники и ошибки;
- request_traces внутри JSON — сообщения, реально переданные модели, сырые финальные
  ответы, отказы проверки, число вызовов и время каждого запроса. HTTP-заголовки и
  API-ключи не записываются. Скрытое reasoning_content прокси не запрашивается и не собирается.

В текстовых логах заменяются значения ключей/токенов и пароль подключения к БД.
Env-файл не копируется. JSON содержит тестовые контакты и исходные фрагменты базы:
он предназначен для локального разбора, а не для публичного репозитория.

Модельные запросы выполняются последовательно с интервалом минимум 15 секунд;
обычно нужно около 15–30 минут, но время зависит от модели и повторов. При 429
прогон останавливается и запоминает cooldown. Повтор той же команды продолжает
незавершённый этап; ранее успешные вопросы/ходы не запрашиваются заново. Ctrl+C
сохраняет завершённые результаты. Если изменён код, модель/поисковые настройки или
база, отпечаток меняется и создаётся новая папка.

`--offline` отключает обращения к модели. Пропущенная проверка БД даёт общий статус
partial, а не ложный complete. Зелёные тесты и supported=true проверяющей модели сами
по себе не доказывают, что все реальные ответы правильны: их нужно сопоставить
с источниками, условиями и текущим вопросом клиента.
