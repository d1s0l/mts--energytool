# API-контракт: черновик для согласования

Статус: предложение, ещё не утверждено командой. Эндпоинты не реализованы.
Примеры JSON описывают формат данных, а не ответы работающего сервера.

Базовый путь: `/api`. JSON, UTF-8. Идентификаторы — UUID в строковом виде;
время — ISO 8601 в UTC. Длительности — миллисекунды.

## Эндпоинты

| Метод | Путь | Результат |
|---|---|---|
| POST | `/api/sessions` | Создать сессию |
| GET | `/api/sessions` | Список сессий |
| GET | `/api/sessions/{session_id}` | История и состояние сессии |
| POST | `/api/sessions/{session_id}/messages` | Отправить сообщение и получить ответ |
| POST | `/api/sessions/{session_id}/lead` | Передать контакты и создать заявку |
| GET | `/api/sessions/{session_id}/lead` | Получить заявку |
| GET | `/api/health` | Готовность сервиса |

Отдельные маршруты для RAG и Debug Mode фронтенду не нужны.
Для первой версии предлагается обычный JSON-ответ без streaming.

## Состояние сессии

- `chatting` — обычная консультация.
- `awaiting_contacts` — консультант предлагает оставить заявку, можно показать форму.
- `lead_created` — заявка сохранена.

Предлагается разрешать продолжение консультации и отказ от заполнения формы.
После создания заявки состояние остаётся `lead_created` и при следующих сообщениях.
Отдельного изменения состояния фронтендом пока не предусмотрено.

## Создание сессии

`POST /api/sessions`, без тела. Ответ `201`:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "state": "chatting",
  "created_at": "2026-11-10T09:00:00Z"
}
```

Кнопка «Новый диалог» вызывает этот метод и переключает интерфейс на новый ID.
Предыдущая сессия и её сообщения сохраняются. После закрытия чата при новом
открытии создаётся новая сессия; просмотр старой истории не делает её контекстом
нового диалога. Событие закрытия и хранения активного ID нужно согласовать с frontend.

## Список сессий

`GET /api/sessions?limit=20&offset=0`. Ответ `200`:

```json
{
  "items": [
    {
      "id": "11111111-1111-4111-8111-111111111111",
      "state": "chatting",
      "created_at": "2026-11-10T09:00:00Z"
    }
  ],
  "total": 1,
  "limit": 20,
  "offset": 0
}
```

Предлагается сортировка по созданию: новые первыми, при равном времени — по ID.
`limit`: 1–100, по умолчанию 20; `offset`: от 0, по умолчанию 0.
Названия диалогов пока не генерируются.

## История сессии

`GET /api/sessions/{session_id}`. Ответ `200`:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "state": "chatting",
  "created_at": "2026-11-10T09:00:00Z",
  "messages": [
    {
      "id": "22222222-2222-4222-8222-222222222222",
      "role": "user",
      "text": "Хочу снизить расходы на электричество",
      "created_at": "2026-11-10T09:01:00Z",
      "debug": null
    }
  ]
}
```

Сообщения идут в порядке разговора. Для начала предлагается вся история без
пагинации; отдельный маршрут сообщений можно добавить при необходимости.
`role`: `user` или `assistant`. Служебные промпты и tool messages не выдаются.
У ответов assistant поле `debug` имеет описанную ниже структуру, чтобы отладка
была доступна и при просмотре истории.

## Отправка сообщения

`POST /api/sessions/{session_id}/messages`:

```json
{
  "text": "У нас три склада, с чего начать?"
}
```

Пустой после удаления пробелов текст недопустим. Предел длины сообщения пока
не определён: согласовать с участником по модели.

Ответ `200` после завершения обработки:

```json
{
  "session_id": "11111111-1111-4111-8111-111111111111",
  "state": "chatting",
  "user_message": {
    "id": "33333333-3333-4333-8333-333333333333",
    "role": "user",
    "text": "У нас три склада, с чего начать?",
    "created_at": "2026-11-10T09:02:00Z",
    "debug": null
  },
  "assistant_message": {
    "id": "44444444-4444-4444-8444-444444444444",
    "role": "assistant",
    "text": "Какая задача сейчас главная: снизить счета или найти потери?",
    "created_at": "2026-11-10T09:02:02Z",
    "debug": {
      "total_ms": 2000,
      "search_ms": 150,
      "generation_ms": 1750,
      "sources": [
        {
          "document_id": "document-id",
          "title": "Название документа",
          "fragment_id": "fragment-id",
          "fragment": "Текст фрагмента, переданного консультанту",
          "score": null
        }
      ]
    }
  }
}
```

Значения и текст выше приведены только для иллюстрации структуры.

### Метаданные отладки

- `total_ms` — полное время обработки на сервере, включая поиск, модель и сохранение;
  не включает передачу по сети до браузера.
- `search_ms` и `generation_ms` — замеры модулей; `null`, если замер недоступен.
- `sources` — фрагменты, фактически переданные консультанту для ответа;
  пустой массив, если их не было. Не весь список кандидатов поиска.
- `score` — необязательная оценка RAG, число или `null`; её смысл и шкалу определяет
  RAG-команда. Frontend не должен интерпретировать её как вероятность правильного ответа.

Debug Mode переключает отображение уже полученных метаданных на frontend.
Ключи, заголовки авторизации и системный промпт в метаданные не включаются.

### Сохранение и параллельные запросы — предложение

Сервер получает историю из БД: frontend не отправляет её повторно.
В одной сессии обрабатывается один запрос к консультанту за раз; второй получает
`409 session_busy`. Разные сессии могут обрабатываться параллельно.

Предлагается сохранять пару user/assistant только после успешной обработки.
При ошибке история и состояние не меняются; ошибку frontend показывает отдельно.
Потеря HTTP-ответа после сохранения всё ещё может привести к повторному сообщению:
до согласования идентификатора запроса frontend не делает автоматический повтор POST.

## Создание заявки

`POST /api/sessions/{session_id}/lead`:

```json
{
  "full_name": "Тестовый Пользователь",
  "phone": "+79990000000",
  "company": "Тестовая компания"
}
```

Только тестовые или выдуманные контакты. Все три поля обязательны; правила
проверки телефона и пределы длины согласовать отдельно.

Frontend отправляет только контакты. Резюме готовится на backend с помощью
модуля консультанта по истории данной сессии. До успешной подготовки резюме
и сохранения заявка не считается созданной. Если операция не удалась, возвращается
ошибка, а не подтверждение создания.

Ответ `201`:

```json
{
  "id": "55555555-5555-4555-8555-555555555555",
  "session_id": "11111111-1111-4111-8111-111111111111",
  "full_name": "Тестовый Пользователь",
  "phone": "+79990000000",
  "company": "Тестовая компания",
  "summary": "Резюме потребности и существенных деталей разговора",
  "created_at": "2026-11-10T09:05:00Z"
}
```

После сохранения состояние сессии — `lead_created`. Предлагается одна заявка
на сессию: повтор с теми же контактами возвращает существующую заявку с `200`,
с другими контактами — `409 lead_already_exists`. Редактирование пока не определено.
Создание заявки одновременно с обработкой сообщения возвращает `409 session_busy`.
Предлагается разрешать отправку контактов и из `chatting`, и из `awaiting_contacts`:
пользователь может сам захотеть связаться с менеджером.

`GET /api/sessions/{session_id}/lead` возвращает ту же структуру с `200`;
если заявки нет — `404 lead_not_found`.

## Ошибки

Предлагаемый единый формат, включая ошибки валидации FastAPI:

```json
{
  "error": {
    "code": "session_not_found",
    "message": "Диалог не найден",
    "details": []
  }
}
```

`details` — список ошибок полей; пустой для ошибок без привязки к полю.
Элемент ошибки поля: `{"field": "phone", "message": "Описание ошибки"}`.
Frontend ориентируется на HTTP-статус и `code`, текст предназначен пользователю.

| HTTP | code | Когда |
|---|---|---|
| 404 | `session_not_found` | Сессия не существует |
| 404 | `lead_not_found` | Заявка отсутствует |
| 409 | `session_busy` | В сессии уже выполняется операция |
| 409 | `lead_already_exists` | Попытка заменить контакты существующей заявки |
| 422 | `validation_error` | Неверный UUID, поля, параметры или пустое сообщение |
| 503 | `consultant_unavailable` | Консультант или необходимый поиск недоступен |
| 503 | `storage_unavailable` | Хранилище недоступно |
| 504 | `consultant_timeout` | Превышен срок обработки консультантом |
| 500 | `internal_error` | Непредвиденная ошибка сервера |

Отказ консультанта из-за отсутствия сведений в базе — нормальный ответ `200`,
а не техническая ошибка. Stack trace и секреты пользователю не возвращаются.

## Готовность сервиса

`GET /api/health`: `200`, если необходимые зависимости готовы; `503` иначе.

```json
{
  "status": "not_ready",
  "checks": {
    "database": "ready",
    "consultant": "not_configured",
    "rag": "not_configured"
  }
}
```

В примере показан неготовый сервис: HTTP `503`.
Допустимые значения проверок: `ready`, `not_ready`, `not_configured`.
Состав обязательных зависимостей уточняется после подключения модулей.
Проверка не должна вызывать платную генерацию при каждом обращении.

## Что нужно подтвердить до реализации

1. С frontend: пути, JSON, обычный ответ без streaming, пагинация списка и
   получение полной истории одним запросом.
2. С frontend: закрытие/повторное открытие чата, просмотр старой истории,
   возможность продолжить выбранную старую сессию.
3. С участником по модели: состояния, сигнал показа формы, подготовка резюме,
   предел сообщения и время ожидания ответа.
4. С RAG-командой: стабильные идентификаторы документа/фрагмента, доступность
   названия и текста фрагмента, смысл score, замеры поиска.
5. С frontend и участником по модели: одна заявка на сессию, отправка контактов
   по инициативе клиента, исправление контактов и проверка телефона.
6. С frontend: поведение при ошибке/обрыве связи, необходимость request_id
   для защиты от повторной отправки сообщения.
7. С лидом: кто имеет доступ к списку сессий, истории, контактам и Debug Mode.
   Перед публичным размещением нужен выбранный механизм ограничения доступа;
   UUID сессии сам по себе не является авторизацией.

Этот HTTP-контракт относится к веб-прототипу. CSV-вход/выход `solution.py`
и интерфейсы Python-модулей согласуются отдельно.
