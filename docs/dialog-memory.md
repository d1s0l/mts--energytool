# Память диалога и действие заявки

## Почему выбран такой подход

Проверено по первичным источникам:

- [Anthropic, Effective context engineering, 29.09.2025](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents): отбор контекста и структурированные записи помогают сохранять сведения в длинной работе.
- [LangGraph, Memory](https://docs.langchain.com/oss/python/langgraph/add-memory): краткосрочная память принадлежит конкретному thread, для production рекомендуется сохранение в БД, в том числе PostgreSQL.
- [OWASP, Prompt Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html): модельный вывод и вызовы инструментов требуют проверки, разрешения контролируются приложением.

Это обоснование принципов, а не требование использовать LangGraph или свидетельство,
что конкретная реализация гарантирует правильность ответов. Здесь использованы
собственные Python-модули и существующая PostgreSQL; новых зависимостей нет.
Между сессиями факты не переносятся — это ограничение кейса.

## Формат и жизненный цикл

`dialog_memory.py` хранит факты с полями field, scope, status, value,
source_message_id и дословной quote. Контакты относятся к client, характеристики —
к default или явно названному клиентом объекту. active_object выбирает текущий объект.
Разные объекты могут иметь разные мощности и количество приборов без перезаписи.

Статусы: provided, tentative, unknown, declined. Неизвестное значение и отказ
сохраняются отдельно от отсутствия поля. Новые факты извлекаются моделью в том же
вызове, что ответ, в memory_updates. Приложение проверяет имя поля, цитату, значение,
пользовательскую роль источника и порядок сообщений. Старое сообщение не заменяет
новое исправление. Дословная опора сама по себе не доказывает правильное отнесение
значения к полю: смысл по-прежнему проверяется моделью и тестами.

Каждая предложенная запись проверяется отдельно: ошибка необязательного извлечения
не отменяет ответ. Приложение назначает client/default, а пересказ неконтактного
значения заменяет дословной цитатой пользователя. Непроверяемые записи пропускаются;
причины доступны в memory_warnings в debug и диагностических JSON. Контакты,
выбор именованного объекта и действие заявки сохраняют строгую проверку.
Работа вечером сама по себе не подтверждает разбивку потребления день/ночь.
Изменение active_object обрабатывается перед остальными предложенными фактами,
поэтому порядок полей в JSON модели не переносит сведения нового объекта в старый.
Уже заданное уточнение учитывается по полю и объекту, включая переформулировки.
При исправлении параметра можно подтвердить изменение без повторного вопроса.
Возврат к уже названному объекту разрешается до генерации по однозначной ссылке
в текущем сообщении. Для составных русских названий учитываются простые падежные
окончания: «первому складу» выбирает сохранённый «Первый склад». Каноническое имя
должно уже существовать в памяти, цитата сохраняется дословно. При упоминании
нескольких объектов автоматического выбора нет; это ограниченный разбор ссылки,
а не полноценное определение сущностей или местоимений.
Явный отказ от контакта и новое явное согласие фиксируются приложением из текущей
реплики. Их сохранение не зависит от того, повторила ли модель memory_updates
при исправлении текста. Отсутствие ответа не считается отказом или согласием.

До генерации в prompt передаются сохранённые факты; текущая реплика передаётся
отдельно и имеет приоритет при исправлениях. После проверки delta получается новое
состояние. Вопрос о уже известном/отклонённом поле подавляется либо отправляется на
исправление. Принятые вопросы отмечаются в asked. Для длинной истории с заполненной
памятью сохраняются последние реплики в бюджете и факты вместо сброса диалога.
Исходная история остаётся в БД для проверки происхождения.

Веб-адаптер читает `sessions.dialog_memory` и `dialog_revision`. Новое состояние,
ответ и заявка записываются одной транзакцией. Проверка revision предотвращает
потерю конкурентного изменения; при ошибке вопрос помечается failed, предложенное
моделью состояние не применяется. Новая сессия получает пустой JSONB из миграции 004.
Текущий прототип читает полную историю для валидации источников; на большом объёме
это можно оптимизировать выборкой нужных сообщений.

## Серверное действие create_lead

В JSON модели action принимает только none или create_lead. Для совместимости
предыдущий lead без action трактуется ядром как предложение create_lead. Никаких
произвольных SQL/HTTP-инструментов модели не предоставлено; нативный function calling
прокси не требуется. `app/lead_actions.py:create_lead` принимает валидные контакты
и резюме, создаёт или обновляет одну карточку под блокировкой сессии.

Перед действием проверяются происхождение контактов, отсутствие противоречия с
текущей памятью и намерение клиента. Резюме использует текущие факты активного объекта;
при их отсутствии — проверенные цитаты клиента. Только успешная транзакция добавляет
подтверждение сохранения. В памяти появляется app-owned lead.status=saved.
Повторный HTTP-запрос с тем же client_message_id возвращает сохранённый ответ.

Формы POST/PUT заявки используют то же действие. Контакты формы становятся отдельным
пользовательским событием в истории и обновляют память; исправленный телефон не
должен быть восстановлен из старой переписки в следующем ходе. Повтор POST с теми же
контактами не создаёт ни новую заявку, ни новый контактный event.

## Проверка

Офлайн: `PYTHONPATH=backend:. python -m unittest discover -s backend/tests -p test_dialog_memory.py -v`.
Проверяются источники фактов, исправления, разные объекты, статусы, пустая новая
сессия, использование памяти в prompt и длинном контексте, запрет неизвестного действия.
Существующие тесты консультанта также прогоняются.

Добавлена интеграционная проверка PostgreSQL: три хода сбора контактов, сохранение
памяти и заявки, повтор одного запроса и пустая новая сессия. Полный запуск:
`TEST_DATABASE_URL=... python -m pytest` из backend после установки requirements-dev.txt.
На агентском стенде нет пакетов PostgreSQL/FastAPI и доступа к Docker, поэтому этот
интеграционный тест здесь не выполнен. Доступность API модели из агентской среды
раньше блокировалась DNS; реальный диалог по новой схеме не объявляется проверенным.

CSV-сабмит включает dialog_memory.py как корневой модуль; каждый входной ID независим.
Встроенная история получает стабильные локальные ID и может наполнить память для
одного ответа. Постоянная запись в PostgreSQL относится только к веб-адаптеру.

`GET /api/sessions/{id}` возвращает dialog_memory владельцу сессии/проверяющему;
это позволяет проверять сохранённые поля и их источники без чтения БД вручную.
Проверено 63 офлайн-теста ядра, памяти и обработки лимитов; отдельно проверен импорт
модулей из плоского ZIP-сабмита. Факт выполнения интеграционного теста БД не заявляется.
