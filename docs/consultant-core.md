# Ядро консультанта

Общее ядро `backend/consultant_impl.py` подключено к FastAPI и CSV-сабмиту.
Генерация использует обычный `/chat/completions`; специальных возможностей
structured outputs и tool calling не требует. Контракт JSON проверяется приложением,
при нарушении разрешён один ремонт ответа. Неудача не превращается в выдуманный ответ.

## Настройка

Для API и сабмита задайте `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`.
Поддержаны альтернативы `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL`/`GEN_MODEL`.
Адрес уже содержит необходимый префикс (например `/v1`); второй префикс не добавляется.
`TEMPERATURE`, `MAX_TOKENS`, `MAX_WORKERS`, `LLM_TIMEOUT` задают генерацию и нагрузку.
Без URL, ключа или идентификатора генератора веб-сервис сообщает неготовность,
а CSV-команда завершает запуск с ошибкой настройки. Фиксированной генеративной модели нет.
Не используйте реальные персональные данные на хакатоне.

RAG настраивается прежними переменными `RAG_MODE`, `EMB_MODEL`, `RERANKER_MODEL`,
`TOP_K`, `RERANKER_TOP_N`. Документы читаются целиком; ограничения выбранных продуктов
передаются отдельно от основного рейтинга. Текстовые таблицы сохраняются более крупными
блоками, чтобы числа не отделялись от условий. Размер prompt ограничен символами;
проверка реального токенного бюджета Qwen остаётся частью прогона с прокси.

## Доступ к API

Создание `POST /api/sessions` доступно анонимно и возвращает `access_token` один раз.
Для последующих операций этой сессии передавайте заголовок `X-Session-Token`.
В БД сохраняется только SHA-256 токена. Сессии, созданные до миграции, доступны
через служебный доступ. UUID сам по себе не даёт доступ к данным.

Для просмотра всех сессий задайте секрет `API_ACCESS_TOKEN` и передавайте
`Authorization: Bearer <API_ACCESS_TOKEN>`. Этот служебный токен разрешает также
проверку истории и заявок всех сессий; его нельзя передавать посетителям сайта.
Отсутствие настройки не открывает общий список. Health остаётся публичным.

Контракт доступа изменился: клиентской части необходимо сохранять токен новой сессии
и прикладывать его к запросам. Код фронтенда в этой ветке не менялся.

## Сообщения и история

В `POST /api/sessions/{id}/messages` кроме `text` передавайте UUID `client_message_id`.
Повтор с тем же ID и текстом возвращает прежнюю завершённую пару сообщений.
Другой текст с тем же ID получает 409. После ошибки тот же ID позволяет повторную
попытку с прежним текстом. Старые клиенты могут не передавать ID, но тогда
повторная доставка не распознаётся как повтор.

Входящее сообщение сохраняется до вызова модели. `status` в истории принимает
`processing`, `completed`, `failed`. При сбое вопрос остаётся доступен проверяющему.
Неудачные обращения не подмешиваются в следующую консультацию как завершённые ходы.
Во время обработки соединение БД не удерживается. Короткая транзакция резервирует
сессию через processing token; после сбоя процесса резерв может быть перехвачен
через 180 секунд. Одновременный новый ход получает 409.

История не переносится между сессиями или CSV ID. Для диалога, превышающего текущий
бюджет 24 000 символов, ассистент просит сузить задачу в новом диалоге вместо
незаметного отбрасывания старых фактов. Структурированное сжатие памяти — дальнейшее
улучшение; текущая версия использует исходные реплики.

## Заявки

Ассистент может предложить собрать ФИО, телефон и компанию. Проверяется, что контакты
действительно встречались в пользовательских сообщениях, а не были сочинены моделью.
При полном наборе и намерении клиента ядро возвращает предложение заявки; API
сохраняет её в транзакции с ответом. Только после этого добавляется подтверждение
«Заявка сохранена в прототипе». При изменении контактов через чат обновляется
существующая карточка.

Резюме строится из выбранных моделью дословных цитат клиента: до шести пунктов по
актуальной задаче. Неподтверждённая цитата отклоняется. Для отдельного запроса заявки
доступен тот же выбор цитат; при недоступности модели сохраняется краткая выдержка
последних пользовательских сообщений. Это обеспечивает проверяемость, но требует
ручной оценки полезности резюме на реальных диалогах.

Отдельный `POST /api/sessions/{id}/lead` сохранён. Повтор с теми же контактами
идемпотентен. `PUT /api/sessions/{id}/lead` позволяет исправить контакты.
Реальной отправки менеджерам нет. В CSV-режиме предложение заявки входит в ответ;
хранение карточек в PostgreSQL выполняется только веб-адаптером.

## Сабмит

Из `backend/`: `python build_submission.py --output dist/submission.zip`.
Архив теперь содержит стандартный `consultant_impl.py` автоматически. Параметр
`--consultant` оставлен для явной подмены реализации.

Сабмит строит индекс при запуске и не зависит от PostgreSQL. Строки обрабатываются
независимо; ошибка одной не отменяет остальные. `SUBMISSION_TIMEOUT` задаёт общий
бюджет (по умолчанию 1100 секунд, максимум 1150). После каждого результата атомарно
обновляется корректный CSV. Окончательно не обработанные ID содержат честный текст
о техническом сбое. Это аварийное поведение, а не успешный ответ; ошибки фиксируются
по номеру строки и типу без тела исключения провайдера.

## Проверки и ограничения

Офлайн: `python -m unittest discover -s backend/tests -p test_consultant_core.py -v`.
Поиск: из `rag/` — `python -m unittest discover -s tests -v`.
Полный backend: из `backend/` — `TEST_DATABASE_URL=... python -m pytest` после установки
`requirements-dev.txt`. Используйте отдельную тестовую БД.

На текущем стенде прошли 17 офлайн-проверок консультанта и batch-обработки,
20 прежних тестов поиска, 40 проверок ожидаемых фрагментов команды. Три найденных
ценовых запроса теперь возвращают ориентир платформы. Проверки с моделью используют
подставные ответы и не доказывают качество Qwen на скрытых вопросах.

Полный backend pytest и PostgreSQL здесь не запущены: зависимости нельзя скачать
из-за недоступного DNS, доступ к Docker socket отсутствует. Проверка реального прокси,
всей схемы API/БД и измерение задержек обязательны перед сдачей.

Числа сверяются с выбранными источниками/словами клиента; ID источников валидируются.
Это не полноценная проверка логического следования: совпадение числа не доказывает,
что оно относится к нужному показателю. Семантические ошибки и полноту оговорок нужно
проверять отдельными диалоговыми оценками. Runtime не использует интернет для ответов.

## Уточнения и стиль ответа

Модель возвращает объяснение в `answer`, следующий вопрос отдельно — в
`follow_up_question`. Приложение добавляет вопрос к видимому ответу. Для уточнения
задачи (`clarify`) и сбора недостающих контактов отсутствие вопроса запускает один ремонт.
Полный ответ о конкретной функции может быть без вопроса: не требуется продолжать
опрос, если уточнение не влияет на текущий ответ.
Повтор уже заданного вопроса также отклоняется. При готовой заявке или явной просьбе
клиента отвечать без вопросов продолжение опроса не требуется.

Служебные обороты вроде «это прямо указано в наших рекомендациях» запрещены
инструкцией; известные шаблоны дополнительно проверяются приложением и отправляются
на переписывание. Источники остаются в отладке. Эти проверки используют подставные
ответы; реальное качество выбора следующего вопроса ещё нужно оценить на модели.

Обычный ответ ориентирован на 30–60 слов: прямой ответ, существенная оговорка и,
если нужно, одно уместное уточнение. Подробности допускаются, когда этого требует вопрос.
Запрещены неподтверждённые сравнения и пояснения из общих знаний модели.

Для `kind=product` внутренний JSON дополнен `answer_support`: части ответа по порядку,
каждая с ID источника и дословной цитатой. Приложение проверяет наличие цитаты в этом
источнике, покрытие всего `answer` и подтверждение чисел цитатой или словами клиента.
Неверное подтверждение запускает одну попытку исправления, затем возвращается ошибка
консультанта. Этот формат используется только внутри генерации; HTTP API не меняется.
Проверка цитат не доказывает логическое следование: модель всё ещё может выбрать
неподходящую цитату или пропустить условие. Качество необходимо проверять на реальных
ответах; механизм не использует заготовленные демо-ответы.

Для вопросов о подключении/замене приборов отдельно проверяется наличие оговорки
о совместимости, моделях или схеме подключения. Классовая поддержка оборудования
не должна становиться обещанием совместимости любой установки. Это эвристика,
а не семантическая проверка достаточности самой оговорки.

## Проверка смысла и релевантности

В ветке исправления качества стандартная фабрика включает отдельную проверку
черновика той же моделью в новом контексте. Проверяются смысловая опора на источники,
ответ на последний вопрос, сохранение условий и уместность уточнения. Одна попытка
исправления получает конкретные замечания; повторно отклонённый ответ не выдаётся.
Обычный ход теперь требует двух вызовов генератора, с исправлением — максимум четырёх
(без учёта ограниченных сетевых повторов). Это увеличивает задержку. Проверяющая
модель тоже может ошибаться; такой подход не гарантирует отсутствие галлюцинаций.

Релевантные фрагменты стоят в контексте перед ограничениями. Ограничения от документов,
не вошедших в первые четыре найденных фрагмента, не вытесняют прямое доказательство.
Объём ответа снова задан как примерно до 150 слов с возможностью расширения.

Прогон реальных ответов (из корня проекта):

```sh
python backend/evaluate_answers.py --env /path/to/env \
  --kb /path/to/knowledge-base.zip --questions /path/to/questions.csv \
  --output /tmp/energytool-answers.json
```

`--baseline` отключает смысловую перепроверку для сравнения с тем же промптом и
поиском. Это не воспроизведение старого коммита. Результат содержит текст ответа,
источники, найденные фрагменты, число вызовов и задержку. Отчёт обновляется после
каждого вопроса; учётные данные в него не записываются. Используйте только тестовые
сведения о клиентах; отчёты не включаются в конкурсный ZIP.

На текущем стенде новая версия проходит 30 офлайн-тестов консультанта, в том числе
проверки отказа при отрицательном вердикте, ремонта и закрытого FAQ без вопроса.
Это тесты на подставных ответах, а не измерение качества реальной модели.
Попытка реального запуска с предоставленным env остановилась на preflight:
DNS имени API недоступен, ответов на вопросы получено 0. Утверждать, что качество
реальных ответов улучшилось, до завершения этого прогона нельзя.

## Ограничения API и возобновление прогона

HTTP 429 теперь выделяется в `ModelRateLimited`: немедленного повторного запроса нет.
Учитывается `Retry-After` в секундах или HTTP-date, при отсутствии — пауза 60 секунд.
Клиент модели помнит cooldown и отклоняет новые обращения локально до его окончания.
В HTTP API ошибка сообщения возвращается как 429 с `Retry-After`; вопрос остаётся в истории.

Диагностический прогон выдерживает минимум 15 секунд между вызовами, включая проверку
и ремонт. Параметр `--interval` позволяет увеличить интервал. При первом 429 весь прогон
останавливается, результат сохраняется. Повторный запуск того же скрипта пропускает
успешные ID и повторяет неудачные; повтор раньше сохранённого cooldown не вызывает API.
`--restart` начинает отчёт заново. Две последовательные прочие ошибки тоже останавливают
прогон. Ctrl+C сохраняет завершённые ответы и прекращает обработку следующих вопросов.

Сырые ответы модели теперь сохраняются в `model_outputs` для диагностики ошибок формата.
Это тестовые данные; отчёт может содержать контакты из тестового диалога и не предназначен
для публикации. Учётные данные запросов в отчёт не включаются.

При включённой смысловой проверке точное совпадение склейки `answer_support.text` с
видимым ответом больше не требуется. Подлинность цитат и числовая опора проверяются,
а полноту и смысл всего ответа оценивает отдельный проверяющий вызов. Это устраняет
ремонт из-за разных формулировок метаданных и ответа. Без смысловой проверки прежнее
строгое требование покрытия сохраняется.

## Итоги первого реального прогона и упрощение формата

В первом завершённом прогоне получено 16 ответов из 18; вопросы 6 и 14 завершились
ошибкой проверки/исправления. Это доля технически полученных ответов, не оценка качества.
Из реальных ответов выявлены лишние ограничения о частных домах, неверный приоритет
вопроса о мощности для автоматизации учёта и смешение вечера с ночью.

В основном режиме со смысловой проверкой генератор теперь возвращает `answer` и ID
источников без `answer_support`: попытка дословно переписать таблицы создавала ложные
отказы и лишние вызовы. Отдельный проверяющий по-прежнему получает исходные документы
и весь видимый ответ. Без проверяющего сохранён строгий формат `answer_support`.
«Вечер» и «ночь» разделены в поисковых синонимах; приоритеты квалификации уточнены
по продуктам. Проверена сохранность 40 прежних поисковых регрессий и 20 unit-тестов.
Эти изменения требуют отдельного реального перепрогона; первый отчёт их не подтверждает.

Для точечного повторения можно передать `--ids 4,5,6,10,14,15,16` и новый `--output`.
Не перезаписывайте первый отчёт: он нужен для сравнения. Качество оценивается вручную
по фактам, существенным условиям, релевантности и полезности следующего вопроса.

## Выбор уточняющего вопроса по неизвестному параметру

По результатам targeted-run.json (8/8 технически сформированных ответов) добавлен
консервативный план следующего вопроса для выявленных сценариев: возраст старой
шиферной кровли, модели подключаемых приборов, существующий учёт по цехам,
дневная нагрузка солнечного проекта, количество приборов у арендодателя и разбивка
день/ночь для архива потерь. Это вопросы о клиенте, не готовые ответы на тестовые ID.
План определяется по тексту диалога, без обращения к CSV ID и без дополнительной LLM.

План передаётся генератору и применяется к видимому ответу: нужный вопрос появляется,
даже если модель вернула null. Явная просьба отвечать без вопросов и готовая заявка
имеют приоритет. Известные по пользовательским сообщениям параметры и уже отвеченные
вопросы не опрашиваются повторно. Извлечение консервативное и эвристическое: оно не
заменяет полноценную модель объектов клиента и не гарантирует распознавание всех
формулировок. Для остальных сценариев остаются prompt и смысловая проверка.

Добавлены проверки конкретных ошибок из реальных ответов: нельзя утверждать выгоду
сетевой станции без дневного профиля, изобретать обязательную схему счётчик-на-цех
или считать получение фотографий доказательством уже внедрённого OCR. При выявлении
такого вывода модель получает причину отказа и одну попытку исправления.

Проверено 43 офлайн-теста консультанта, включая приоритет явного отказа от вопросов,
неизвестные параметры и запрет повторного опроса. Новые правила ещё требуют повторного
прогона модели: успешный targeted-run.json относится к предыдущей версии кода.
