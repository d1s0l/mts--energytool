# MTS Energytool

Frontend, FastAPI, PostgreSQL и командный модуль RAG. Доступны создание сессий и чтение истории.
Генерация ответов и резюме заявок ожидает подключения модуля модели.

## Запуск через Docker

Скопируйте `.env.example` в `.env` и укажите `KNOWLEDGE_BASE_PATH` — абсолютный
путь к существующему `knowledge-base.zip`. Архив хранится вне репозитория.

```sh
docker compose up --build
```

- Frontend: http://localhost:3000
- Swagger: http://localhost:8000/docs
- OpenAPI: http://localhost:8000/openapi.json

PostgreSQL хранит данные в volume `pgdata`. При старте backend открывает пул
подключений к БД и применяет SQL-миграции. При старте также один раз строится RAG-индекс.
Если база знаний отсутствует или не читается, запуск завершается ошибкой.
Frontend пока не вызывает API сессий.

Для изменения локального пароля скопируйте `.env.example` в `.env` в корне.
Пароль по умолчанию предназначен для локальной разработки. При смене пароля
существующего PostgreSQL нужно также изменить пароль роли в самой БД.

## Backend локально

Используйте Python 3.12 (та же версия, что в Docker).

```sh
cd backend
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
cp .env.example .env
```

Из корня проекта запустите БД с локальным портом:

```sh
docker compose -f compose.yaml -f compose.local.yaml up -d postgres
```

Затем из `backend/`:

```sh
PYTHONPATH=.. uvicorn app.main:app --reload
ruff check .
```

При изменении пароля согласуйте DATABASE_URL в `backend/.env` с корневым `.env`.
Интеграционные тесты запускаются из `backend/` на реальном PostgreSQL:

```sh
TEST_DATABASE_URL=postgresql://energytool:energytool@localhost:5432/energytool python -m pytest
```

Используйте тестовую БД: тесты создают и удаляют только свои временные схемы
со случайными именами. Нужны права на создание схем. Без `TEST_DATABASE_URL`
интеграционные тесты пропускаются.

## Структура backend

- `app/main.py` — приложение FastAPI и жизненный цикл пула БД.
- `app/config.py` — настройки окружения.
- `app/db.py` — подключение PostgreSQL.
- `app/migrate.py`, `app/migrations/` — запуск и версии SQL-миграций.
- `app/api/sessions.py` — создание сессии, список и история.
- `app/schemas.py` — модели ответов API сессий.
- `app/consultant.py` — место для интеграции консультанта.
- `app/rag.py` — асинхронная обвязка поиска из корневого `rag/`.
- `solution.py` — CSV-адаптер автоматической проверки.
- `build_submission.py` — упаковка корневых модулей в ZIP.

Контракты API, дальнейшие изменения схемы БД, интеграция LLM/RAG и формат сабмита требуют согласования.
LLM SDK, LangGraph и векторная БД пока не добавлены: выбор зависит от команды.

## Хранение данных

- `sessions`: UUID, состояние, время создания.
- `messages`: UUID, сессия, порядок, роль, текст, JSONB-метаданные отладки и время.
- `leads`: UUID, сессия, ФИО, телефон, компания, резюме и время создания.
- `schema_migrations`: применённые миграции и их контрольные суммы.

Сообщения и заявки ссылаются на существующую сессию. Каскадного удаления нет:
БД не позволяет удалить сессию с историей. Сессия может существовать без
сообщений и заявки. Количество заявок на сессию пока не ограничено.
JSONB позволяет уточнять метаданные отладки без изменения таблицы.
Проверка формата телефона и переходы состояний будут реализованы отдельно.

Миграции применяются при старте backend в транзакции с блокировкой параллельных
запусков. Повторный запуск не очищает таблицы. При ошибке изменения текущего
запуска миграций откатываются, приложение не запускается.

Для изменения структуры добавляйте следующий файл, например
`backend/app/migrations/002_add_field.sql`. Уже применённые файлы не редактируйте:
проверка контрольной суммы остановит запуск. Исправления вносятся следующей
миграцией; автоматического отката версий нет. Перед изменением рабочей БД
делайте резервную копию.

## Доступные эндпоинты

- `POST /api/sessions` — новая сессия, ответ 201.
- `GET /api/sessions?limit=20&offset=0` — список новых сессий первыми.
- `GET /api/sessions/{session_id}` — состояние и сообщения в порядке разговора.

Создание сессии не удаляет предыдущие диалоги. Неизвестный ID возвращает 404,
некорректный UUID или пагинация — 422. Список и total читаются в одном снимке БД.
POST `/api/sessions/{session_id}/messages` принимает JSON с полем `text`.
Консультант подключается через `create_app(consultant=...)`. Без него API отвечает
`503 consultant_unavailable`. После ответа обе реплики сохраняются одной транзакцией.
Поле title пока отсутствует; frontend должен отображать ID или самостоятельно выбрать подпись.
GET /api/health возвращает готовность сервиса и отдельных зависимостей.

## Подключение RAG

Код `rag/` перенесён без изменений из `origin/feature/rag-search` (коммит `1ec1129`).
Дополнительные пакеты ему не нужны. Веб-приложение создаёт один SearchService
в `app.state.search`; `await service.search(question, history)` выполняет поиск
через поток, не блокируя event loop. Формат history — список role/content.
Метод debug_sources преобразует найденные фрагменты в формат нашего API;
после подключения LLM возвращать следует только фактически использованные фрагменты.
Отдельного HTTP-метода поиска нет. Это подготовка интеграции с консультантом.

Для локальной разработки задайте путь к архиву в `backend/.env`.
`RAG_MODE=local` не обращается к сети. Для `auto`/`hybrid` укажите адрес и ключ
прокси организаторов: `LLM_BASE_URL`, `LLM_API_KEY`, модель `EMB_MODEL` и при
необходимости `RERANKER_MODEL`. Полный список параметров — в `rag/README.md`.
В Compose часть параметров передаётся явно; дополнительные параметры RAG
добавляйте в environment сервиса backend при необходимости.
`MAX_WORKERS` (1–8, по умолчанию 3) ограничивает параллельный поиск.
На старте индекс строится один раз. При сетевых ошибках RAG может перейти
к локальному поиску — проверяйте mode и warnings в результате.

Docker backend теперь собирается из корня проекта, чтобы включить `rag/`:
`docker build -f backend/Dockerfile .`. База подключается read-only bind mount,
в образ не копируется. Поиск не хранит историю сессий: историю передаёт вызывающий код.


Удаление чата выполняет `DELETE /api/sessions/{session_id}` (204).
Это мягкое удаление с сохранением сообщений и заявок. Список и чтение сессии
поддерживают `include_deleted=true` для проверки сохранённой истории.
При старте применяется миграция `002_soft_delete_sessions.sql`.


## API заявок

- POST /api/sessions/{session_id}/lead принимает full_name, phone, company.
- GET /api/sessions/{session_id}/lead возвращает сохранённую заявку с резюме.

Для резюме передайте асинхронную функцию через
create_app(lead_summarizer=...). Интерфейс LeadSummarizer определён в
backend/app/consultant.py: функция принимает history из role/content и
возвращает непустой текст резюме. ФИО, телефон и компания сохраняются из формы.
Без подключённой функции создание возвращает 503. Правила повторной отправки,
валидации и ошибок описаны в docs/api-contract.md.


## Готовность

GET /api/health проверяет PostgreSQL, индекс RAG и наличие модулей консультанта
и генератора резюме. Полная готовность возвращает 200, неполная — 503.
Проверка не обращается к API модели. Пока модули модели не подключены, 503 ожидаем.
Это readiness-проверка полного сценария, а не проверка существования процесса.

## CSV-сабмит

Сабмит читает DATA_DIR/questions.csv (UTF-8, колонки id,question) и
DATA_DIR/knowledge-base.zip. DATA_DIR по умолчанию равен data.
RAG-индекс строится один раз. История из question разбирается на role/content;
консультант получает последнюю реплику отдельно, история между ID не переносится.
MAX_WORKERS задаёт 1–8 параллельных обработчиков (по умолчанию 3).
Тайм-аут одного ответа — 60 секунд.

Нужно получить от участника по модели consultant_impl.py с синхронной фабрикой
create_consultant(), возвращающей асинхронный вызываемый объект по интерфейсу
Consultant из consultant.py. Аргументы вызова — text, history, search,
результат — ConsultantReply. Поиск вызывается через await search.search(...).
Реализация читает параметры LLM_BASE_URL, LLM_API_KEY, LLM_MODEL и настройки
генерации из окружения платформы. Дополнительные зависимости модели должны
входить в разрешённый набор и добавляться в requirements-submission.txt.

Сборка из корня проекта:

```sh
backend/.venv/bin/python backend/build_submission.py --consultant /path/to/consultant_impl.py
```

Дополнительные корневые .py-модули консультанта можно передать через
повторяемый аргумент --module /path/to/module.py. Импорты реализации должны
работать с корневыми модулями без backend/app и других вложенных пакетов.
Архив backend/dist/submission.zip содержит solution.py, consultant.py,
rag_search.py, requirements.txt и переданные модули.
Веб-зависимости, PostgreSQL, ключи, данные, конфигурации и готовые индексы
в архив не включаются. Локальная база знаний подключается только при запуске.

Без --consultant сборщик создаёт подготовительный архив с предупреждением.
При запуске такого архива solution.py завершится с кодом 1 и сообщением
о необходимости подключить consultant_impl.py. Загружать его для оценки рано.

Для локального прогона распакуйте собранный ZIP в отдельную папку, создайте
там Python-окружение и установите requirements.txt. Затем:

```sh
DATA_DIR=/path/to/local-input python solution.py
```

Для демонстрационных вопросов используйте локальную копию demo_questions.csv
под именем questions.csv рядом с knowledge-base.zip. Настройки API передайте
через окружение. Скрипт не загружает .env самостоятельно.

При успешном прогоне создаётся submission.csv в текущем каталоге с ровно
двумя колонками id,answer. ID и порядок строк сохраняются. Запятые, кавычки
и переносы строк экранируются стандартным CSV. Ответ длиннее 10000 символов
считается ошибкой, а не обрезается. Файл заменяется атомарно только после
успеха всех тест-кейсов. При ошибке процесс возвращает 1 и не создаёт
частичный результат. Предыдущий submission.csv, если он был, остаётся прежним.

Проверки PostgreSQL и готовности веб-компонентов находятся в GET /api/health.
Автоматический сабмит работает отдельно от веб-сервера и БД.
